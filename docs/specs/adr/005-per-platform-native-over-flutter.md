# ADR-005: Dart/Flutter をやめ、プラットフォーム単位の Native 実装にする

- **ステータス**: Accepted（2026-09-27。Dart 実装の保存場所のみ未決だが決定を妨げない）
- **決定日**: 2026-09-27（ドラフト）
- **Supersedes**: [ADR-001](./001-dart-flutter-over-swift.md)

## コンテキスト

ADR-001 は「Swift 版は macOS 専用になる」という懸念から、Dart/Flutter の monorepo
（packages/core + apps/desktop）で全面再構築した。しかし実際の状況は次のとおり。

1. 配布は Homebrew cask + GitHub Release に定まり、OS ごとに公式チャネル（brew / winget）を
   通す形になった。どのみせ OS 単位のビルド・署名が不可避で、Flutter の利点は薄かった
2. トレイ常駐・ポップオーバー・フォントレンダリング（design.md 6 章・7 章）など、
   常駐アプリの作り込みはネイティブ API に及ばれない。Flutter 側はプラグイン依存という
   新たなリスク面を抱えた（tray_manager 等の選定・審査コストが既に発生した）
3. macOS には先行実装（claude-session-memo）として Swift での検証済みコードが残る。
   移植の拠り所がある
4. 開発体制は 1〜2 人。スタックをまたいだ単一コードベースより、OS ごとの素直な実装のほうが
   保守が軽い

そして本 ADR の前提として、**Dart をやめ、プラットフォーム単位で Native 実装する**という
方針が決められた。ここにその記録と、構造上の帰結を記す。

## 決定

**Dart/Flutter を廃止し、各 OS の公式言語・公式 UI スタックで実装する。**

- macOS: Swift + AppKit（SPM）。先行実装の資産を活かす
- Windows: C#/.NET + WPF（導入時）
- Linux: 保留
- MCP サーバー: **アプリ内蔵の CLI サブコマンド `moost mcp` を主とする**。ユーザに Node の有無を前提としない（アプリ単体で完結）。Dart 実装の mcp_server はリファレンスとして残す

**共通ロジック層（core）は共有しない。** 各実装がもつ代わりに、データ契約と検査データを
リポジトリの `spec/` に置き、同一テストによる適合検証で実装間のズレを検知する。
Dart 実装は当面リファレンス実装としてリポジトリに残す。

リポジトリは monorepo を継続し、リリースはプラットフォーム別接の git タグ
`macos/v<x.y.z>` / `windows/v<x.y.z>` を単一の情報源とする。バージョンはプラットフォーム
ごとに独立した系列とし、タグ push からはそのプラットフォームのビルドのみを走らせる
（詳細は [移行計画](../native-migration-plan.md) の 4〜6 章）。

## 理由

| 観点 | Flutter 継続 | プラットフォーム別 Native |
|------|-------------|--------------------------|
| トレイ常駐・ポップオーバー | プラグイン依存。常駐特有の制約に plugin 経由で格闘 | ネイティブ API を直接使う。先行実装で検証済み |
| macOS 実装コスト | 実装済み（ただし残すか否かの判断を先送り） | Swift 先行実装から出発でき最も短い |
| Windows/Linux | Flutter で理論上対応可能だが、実需の実現が薄い | OS ごとに順当な技術を選べる |
| 実行物・メモリ | Flutter ランタイム分のかさみがある | 各 OS の標準形。軽い |
| 配布 | brew/winget はどちらを通っても同じ道 | 同じ。加えて署名・公証の方が厳しい |
| 共通ロジック | 単一実装でズレがない（利点） | 各実装。spec/ の検査でズレを検知する |

採用の決め手は次の 2 点。

1. **実装の大半は UI であり、UI は共有できない。** 共有できる core は小さいので、
   重複のコストは許容できる範囲。共有層の設計に払うコストより、
   `spec/` による共通化の推進を選ぶ
2. **リスクの管理**: 実装間の差異（ズレ）は危険。対策として、データ仕様（memos/settings の
   スキーマ）とテストデータ（history.jsonl 等の Fixture）を公開し、
   毎回テストを通し、実装の比較・検討を重ねる

## 影響

- ADR-001 は superseded となる。ただし「UI 非依存ロジックを分離して守る」という
  原則自体は有効。各実装でも core 層（プラットフォームによらない読み）を分離する
- データ契約（`schemaVersion`）は形式不変。保存ディレクトリは native 世代で
  `~/.moost/v2/` に新設し、初回起動時に v1 からの移行処置を実行する（移行後 v1 は読み取り専用）
- リファレンス実装（Dart）は conformance 合格後に削除する
- release.md / design.md の関連章節は移行計画の資料に従い改訂する
- ドキュメントの作成・編集・公開・運用方針は現状のまま（Keep a Changelog、SemVer、
  タグ push による自動化）
